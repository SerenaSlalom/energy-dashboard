# Mock data model notes

`src/data/energy-usage.json` is invented, internally-consistent hourly load
data — no real utility, city, or ratepayer data. It was generated by a
one-off script (not committed — this file documents the approach so it can
be reproduced or adjusted without redoing the trial-and-error).

## The shape is the point

The brief's whole narrative depends on the load curve actually looking like
two peaks with a dip between them in summer, a single plateau in winter, and
muted in-between versions in spring/fall. That shape does **not** fall out
naturally from `residential + commercial + industrial − solar` with
naively-chosen parameters — the first few attempts produced a spurious
morning peak, or a dip so deep it went negative, or an evening peak smaller
than the midday one (backwards from the story). Getting the shape right took
iterating on parameters against printed output, not just picking numbers
that looked plausible on paper.

If you regenerate this data, preserve these shape constraints (verify by
printing the `netLoad` array per season, not just eyeballing the chart):

- **Summer**: three local extrema in `netLoad` — a midday **peak** (~hour
  11), an afternoon **dip** (~hour 16, allowed to go below the overnight
  floor — that's the realistic "duck curve" belly, not a bug), and an
  evening **peak** (~hour 20) that is clearly the highest point of the day.
  The evening peak must be larger than the midday peak — the narrative is
  that solar is *shrinking* the old peak while EVs *grow* a new, bigger one.
- **Winter**: no real dip — heating demand plus weak solar should read as
  one elevated plateau, not two separated bumps.
- **Spring / Fall**: the same three-extrema shape as summer, but with much
  smaller amplitude swings — muted enough to read as "transitional," not a
  second dramatic peak.

## How the curves are built

Each sector series is a sum of a flat baseline plus one or more Gaussian
"bumps" (`height * exp(-distance² / (2 * width²))`, wrapped for the 24-hour
clock) centered on the hour that sector's load should peak — e.g. commercial
cooling centered near midday, residential evening use centered after work.
Solar is a single wide Gaussian, deliberately centered *later* than the
commercial peak (early-to-mid afternoon rather than exactly noon) — that
offset is what produces the afternoon dip instead of just canceling out the
midday peak.

`netLoad = residential + commercial + industrial + evCharging − solar`,
rounded to one decimal. EV charging is summed in explicitly (not folded into
the residential curve) so the AI insight copy's driver breakdowns
(e.g., "~40% EV charging") stay traceable to an actual series.

## Points of interest

Each season's `pointsOfInterest` entries pair an hour with the AI insight
copy shown when that marker is clicked. The `hour` values must match an
actual local peak or dip in that season's `netLoad` array — if you change
the curve shape, re-check these hours line up with the new extrema, or the
click target and the insight text will disagree with what the chart shows.

## Trend/projection data

`trend.historical` and `trend.projection` are directional, hand-picked
figures illustrating a plausible trajectory (risk-window months widening as
solar/EV adoption climbs) — not a model output. `trend.projection.years`
includes the last historical year as its first element so the two line
segments connect visually; `TrendProjectionView.vue` splits the solid/dashed
line style at that boundary via `historicalLength`, not by re-deriving it
from the data each time.
